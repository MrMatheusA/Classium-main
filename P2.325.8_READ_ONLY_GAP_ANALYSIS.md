## 2. Reconstrução do Baseline das Políticas e Auditoria Semântica

### 2.1. Tabela `public.platform_members`
Nas etapas anteriores, coexistiram duas referências de nomenclatura:
- `platform_members_select_admin` (documentada na evidência E-02 de P2.325.5).
- `platform_members_select_policy` (documentada em migrações preliminares e na especificação P2.325.2).

#### O Problema das Políticas Permissivas Concorrentes (Avaliação em OR):
No PostgreSQL, se ambas as políticas estiverem ativas e forem do tipo `PERMISSIVE` para o comando `SELECT`:
$$\text{Acesso Concedido} = \text{Condição}(\text{Policy}_1) \lor \text{Condição}(\text{Policy}_2)$$
- Se `platform_members_select_policy` existir remotamente com a expressão `USING (user_id = auth.uid())`, qualquer usuário logado pode visualizar seu próprio vínculo.
- Se `platform_members_select_policy` existir com `USING (true)` (como ocorreu em tabelas legadas antes do hardening), a tabela inteira estaria desprotegida contra leitura.
- **Falha Identificada no Candidato P2.325.6:** O script realizava `DROP POLICY IF EXISTS platform_members_select_admin`, mas na pré-condição excluía da contagem de políticas inesperadas:
  `pol.polname NOT IN ('platform_members_select_policy', 'platform_members_select_admin')`
  Isso significa que, se `platform_members_select_policy` existisse no banco com qualquer regra (mesmo insegura), o script tolerava sua presença sem validar sua expressão!
- **Diretriz Mandatória de Correção:** Não se pode tolerar `platform_members_select_policy` por simples lista branca de nomes. O script deve exigir a inspeção exata de `pg_policy` para determinar se ela existe, qual sua expressão `polqual`, ou removê-la explicitamente se for uma política legada deprecada.

### 2.2. Tabela `public.audit_logs`: A Divergência Crítica entre `IN (SELECT ...)` e `EXISTS (...)`
No arquivo `P2.325.6_CANONICAL_FIX_CANDIDATE.sql`, a política `audit_logs_select_authorized` foi especificada como:
```sql
CREATE POLICY audit_logs_select_authorized
    ON public.audit_logs FOR SELECT TO authenticated
    USING (
        public.is_platform_admin()
        OR (
            organization_id IS NOT NULL 
            AND EXISTS (
                SELECT 1
                FROM public.organization_members om
                WHERE om.organization_id = audit_logs.organization_id
                  AND om.user_id = auth.uid()
                  AND om.role IN ('gestor', 'admin')
                  AND om.is_active = true
            )
        )
    );
```

Entretanto, as migrações padrão do Classium (como `20260927_partner_members_select_policy.sql` e `20260927_partners_rls_policies.sql`) utilizam o padrão:
```sql
organization_id IN (
    SELECT om.organization_id
    FROM public.organization_members om
    WHERE om.user_id = auth.uid()
      AND om.role IN ('gestor', 'admin') -- ou 'gestor'
      AND om.is_active = true
)
```

#### Confronto Técnico: `IN (SELECT ...)` versus `EXISTS (...)`

| Critério de Comparação | Padrão `IN (SELECT ...)` | Padrão `EXISTS (...)` | Divergência e Impacto Técnico |
|---|---|---|---|
| **Representação no Catálogo (`pg_get_expr`)** | Decompilado pelo PostgreSQL como `(organization_id = ANY (SELECT om.organization_id FROM ...))` | Decompilado como `(EXISTS (SELECT 1 FROM ... WHERE (om.organization_id = audit_logs.organization_id) ...))` | **Textualmente incompatível.** Um teste de pré-condição ou rollback que compare strings exatas falhará fatalmente se não souber qual formato está gravado no catálogo remoto. |
| **Tratamento de Nulos (`organization_id = NULL`)** | Em SQL tri-valorado, `NULL IN (...)` avalia para `UNKNOWN` (falso em RLS). Mas se a subquery retornar algum `NULL`, a negação ou avaliação de listas pode causar comportamento anômalo. | O predicado explícito `organization_id IS NOT NULL AND EXISTS (...)` é determinístico e imune a anomalias de nulos na subquery. | Semântica semelhante no caso positivo, mas sutilmente diferente em casos de borda com valores nulos. |
| **Comportamento do Planejador de Consultas** | Pode ser executado via Hashing da subconsulta (materializando os IDs das organizações do usuário uma única vez por query). | Executado como SubPlan correlacionado linha a linha contra o índice de `organization_members`. | Diferença de custo de execução e plano gerado pelo PostgreSQL Optimizer. |
| **Veredito de Baseline:** | **NÃO COMPROVADO se o original é IN ou EXISTS.** | **NÃO COMPROVADO se o original é EXISTS.** | **STATUS: PENDENTE.** É estritamente proibido presumir que o banco remoto usa `EXISTS` sem visualizar a saída literal de `pg_catalog.pg_get_expr(polqual, polrelid)`. |

## 3. Auditoria Crítica das Pré-Condições do Candidato P2.325.6

O arquivo `P2.325.6_CANONICAL_FIX_CANDIDATE.sql` avançou significativamente, mas a auditoria estática identificou 4 fragilidades que impedem sua execução como script final de produção:

### Fragilidade 1: Verificação Frouxa via Substring `ILIKE '%...'`
- **Trecho no SQL:**
  ```sql
  IF v_policy_qual NOT ILIKE '%is_platform_admin%' THEN ...
  IF v_policy_qual NOT ILIKE '%organization_members%' ... THEN ...
  ```
- **Risco:** O operador `ILIKE '%is_platform_admin%'` valida apenas se a palavra está contida no texto. Se um atacante ou uma falha de migração tivesse alterado a política para:
  `USING (is_platform_admin(auth.uid()) OR true)`
  ou
  `USING (is_platform_admin(auth.uid()) AND organization_members.id IS NOT NULL)`
  O teste aceitaria a expressão como válida! A verificação não garante a integridade estrutural da regra.
- **Correção Necessária:** O teste de baseline deve comparar a expressão canônica completa, normalizada (remoção de espaços duplos e quebras de linha), ou validar explicitamente a ausência de operadores espúrios.

### Fragilidade 2: Omissão de Validação do Proprietário e ACL da Função Conflitante
- **Trecho no SQL:** Ao checar `pronargs = 0`, o script valida apenas se `ret_type = 'boolean'`.
- **Risco:** Se já existir uma função `public.is_platform_admin()` criada por outro proprietário, ou com `SECURITY INVOKER`, ou com `search_path` inseguro, ou já vinculada a outros privilégios de `anon`, o script tentaria atualizar com `CREATE OR REPLACE`, o que falhará se o usuário da transação não tiver permissão de substituir função de outro dono, ou poderá herdar dependências indesejadas.
- **Correção Necessária:** Abortar com `RAISE EXCEPTION` caso já exista qualquer função sem argumentos no catálogo, exigindo intervenção e saneamento manual prévio.

### Fragilidade 3: Tolerância Injustificada da Política `platform_members_select_policy`
- **Trecho no SQL:**
  ```sql
  AND pol.polname NOT IN ('platform_members_select_policy', 'platform_members_select_admin')
  ```
- **Risco:** Tolerância silenciosa a uma segunda política de leitura. Em PostgreSQL, políticas `PERMISSIVE` acumulam privilégios via `OR`. Se a política antiga existir, ela poderá anular o isolamento pretendido.

## 4. Auditoria Exaustiva de Permissões: A Concessão Indevida à `service_role`

Na etapa P2.325.6, o script introduziu o comando:
```sql
REVOKE ALL ON FUNCTION public.is_platform_admin(uuid) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.is_platform_admin(uuid) TO service_role; -- << PONTO CRÍTICO
```

### Análise da Concessão de `service_role` na Função com UUID:
1. **Evidência do Catálogo Real:** A evidência E-03 confirmou que a ACL original no Supabase oficial era:
   `{postgres=X/postgres}`.
   Ou seja: **Nem mesmo a `service_role` possuía `EXECUTE` sobre a função `is_platform_admin(uuid)`!**
2. **Dependência Comprovada no Repositório:** A busca em todo o codebase local confirmou que **não existe nenhuma chamada** à função com UUID via `service_role`.
3. **Princípio do Menor Privilégio:** Conceder `EXECUTE` a `service_role` sem necessidade comprovada viola a diretriz de não alteração de superfícies desnecessárias. A `service_role` opera primariamente com `BYPASSRLS` nas tabelas; ela não necessita da função legada para executar consultas administrativas.
4. **Decisão de Auditoria:** O `GRANT EXECUTE` da função legada com UUID para `service_role` **DEVE SER RETIRADO** do candidato. A função antiga deve permanecer estritamente com sua ACL original intacta:
   `REVOKE ALL ON FUNCTION public.is_platform_admin(uuid) FROM PUBLIC, anon, authenticated, service_role;`

### Matriz Corrigida de Permissões

| Assinatura da Função | Papel | Situação Atual Documentada | Proposta Auditada P2.325.8 | Justificativa Técnica Rígida |
|---|---|---|---|---|
| **`is_platform_admin()`** (Nova / Canônica) | `PUBLIC` | Inexistente | `REVOKE ALL` | Bloqueio de herança implícita do PostgreSQL. |
| **`is_platform_admin()`** (Nova / Canônica) | `anon` | Inexistente | `REVOKE ALL` | Clientes anônimos não possuem JWT (`auth.uid() = NULL`). Bloqueia acesso RPC via API aberta. |
| **`is_platform_admin()`** (Nova / Canônica) | `authenticated` | Inexistente | `GRANT EXECUTE` | **Requisito mandatório para sanar o SQLSTATE 42501.** Necessário para o PostgreSQL avaliar as políticas RLS. |
| **`is_platform_admin()`** (Nova / Canônica) | `service_role` | Inexistente | `GRANT EXECUTE` | Permite que rotinas de backend com chave de serviço consultem o endpoint RPC de autorização. |
| **`is_platform_admin(uuid)`** (Legada OID 17812) | `PUBLIC` | Sem permissão | `REVOKE ALL` | Preservação do baseline. |
| **`is_platform_admin(uuid)`** (Legada OID 17812) | `anon` | Sem permissão | `REVOKE ALL` | Bloqueio total de enumeração. |
| **`is_platform_admin(uuid)`** (Legada OID 17812) | `authenticated` | Sem permissão (`42501`) | `REVOKE ALL` | Impede que usuários externos passem UUIDs de terceiros via RPC. |
| **`is_platform_admin(uuid)`** (Legada OID 17812) | `service_role` | Sem permissão | **`REVOKE ALL` (Mantido sem GRANT)** | **Decisão P2.325.8:** Não há dependência comprovada que justifique a concessão. Manter estritamente como `{postgres=X/postgres}`. |

## 5. Auditoria do Rollback e Inviabilidade de "Rollback Determinístico" sem Baseline Bruto

No relatório P2.325.6, o procedimento de reversão foi descrito como "100% determinístico". Esta auditoria contesta formalmente essa afirmação:

### Por que o Rollback do P2.325.6 NÃO é 100% Determinístico?
1. **Incerteza na Cláusula de `audit_logs`:** Se o banco oficial de produção foi configurado originalmente com `IN (SELECT ...)`, o rollback do P2.325.6 executaria `CREATE POLICY ... USING (... EXISTS (...))`. Isso significaria que, após um rollback, o banco **não voltaria ao estado original**, mas sim a um estado sintaticamente alterado!
2. **Incerteza sobre `platform_members_select_policy`:** Se existia uma política com esse nome antes do deploy e ela foi excluída, o rollback proposto recria apenas `platform_members_select_admin`, deixando a tabela com perda permanente de uma regra preexistente.
3. **Critério Rígido de Governança:** Um rollback só pode ser classificado como determinístico se os comandos DDL de restauração forem gerados a partir do resultado textual literal de `pg_dump` ou `pg_catalog.pg_get_expr` capturado diretamente daquela instância.

## 6. Requisitos Objetivos para o Novo Candidato (P2.325.9 Proposta)

Para que um novo candidato SQL possa ser considerado homologável para apresentação humana, ele deve implementar:

1. **Aborto Imediato perante Função Canônica Preexistente:**
   Se `SELECT 1 FROM pg_proc WHERE proname = 'is_platform_admin' AND pronargs = 0` retornar verdadeiro, abortar imediatamente com `RAISE EXCEPTION 'PRECONDITION_FAILED: Função sem argumentos já existe no catálogo.'`, evitando sobrescritas acidentais de tentativas anteriores.
2. **Validação de Baseline Estrito (Anti-ILIKE):**
   A validação semântica das políticas ativas deve verificar se a contagem de políticas em `platform_members` é exatamente igual a 1 (ou o número exato apurado na extração bruta). Se houver qualquer política adicional, abortar.
3. **Não-Concessão de Privilégios à Função com UUID para `service_role`:**
   A função com UUID deve ter sua ACL mantida idêntica ao catálogo original `{postgres=X/postgres}`, revogando de todos os papéis de API.
4. **Normalização de `SET search_path = ''`:**
   Manter o isolamento completo contra CWE-426, qualificando `public.platform_members`, `public.roles` e `auth.uid()`.
5. **Correção Consolidada de `r.scope_type`:**
   Manter o predicado `r.scope_type = 'platform'`.
